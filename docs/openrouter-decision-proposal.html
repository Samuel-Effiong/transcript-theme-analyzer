01

Executive summary

The request. Approve a $100 prepaid OpenRouter balance and a paid pilot on 50 transcripts (estimated cost: under $5). If the pilot's results hold up, adopt a low-cost model as the pipeline's production default, with a premium Claude model re-scoring the small subset of transcripts that actually reach publication.

Nothing has to be built. The pipeline is already provider-agnostic. Its configuration already names OpenRouter as the provider and a DeepSeek model as the default. Changing which model does the work is one line in a configuration file — not an engineering project, not a migration, not a cost. We are not asking permission to build the switch. We are asking permission to use the one that is already there.

The number. Analysing all 1,800 transcripts for one theme costs roughly $154 on Claude Opus 5 and roughly $1.89 on DeepSeek V4 Flash — a factor of about 81×. Against Claude Sonnet 5 the factor is about 33×. These are modelled from the pipeline's own configuration constants and today's published prices; the calculator is in the repository and anyone can re-run it.

The argument is about iteration, not about a single invoice

$154 is not a frightening number, and this proposal will not pretend it is. Frontier model prices have fallen sharply — Claude Opus 5 costs a third of what the previous Opus generation did. One run of one theme at frontier prices is affordable.

But a run is never one run. Every theme is a full pass over the corpus. Ten themes is ten runs. Every prompt refinement, every schema correction, every re-analysis after new transcripts arrive is another full run. That is where the multiplier bites:

The core of the case

An expensive model does not merely cost more. It makes the team afraid to run the pipeline. A budget that punishes iteration produces worse research, because themes that cannot be justified on an invoice simply never get explored, and a prompt nobody dares re-run never gets improved. The cheap model does not buy us a discount. It buys us permission to be thorough.

What we are not saying

This is not a proposal against Claude. Claude is excellent, and its chat interface is the best interactive tool of its kind — we are not proposing to cancel it, and the team should keep using it for exploratory and conversational work. Nor is it a claim that all models are equally capable. It is a narrower claim: our task is a bounded, well-specified one, and the current generation of mid-tier models does it reliably. We are paying frontier prices for a commodity operation.

Before anything else, one correction of a common assumption

The Claude subscription we already pay for cannot fund this work — at any tier. A Claude subscription buys seats on Claude's chat apps; it does not include API access, and it cannot issue the key an application needs. In Anthropic's own words, it "doesn't include access to the Claude API or Console." These are two separate products on two separate accounts with two separate invoices. So the choice in front of us is not subscription versus API — that money is already committed elsewhere and cannot be redirected. The choice is which API to buy, and this document argues for the one that is not locked to a single vendor. Section 5 sets out the full distinction, including the one narrow exception and why it does not apply to us.

And OpenRouter is not a bet against Claude either. Claude Opus 5 is available through OpenRouter at exactly the same published price as buying it from Anthropic directly — $5 and $25 per million input and output tokens. Choosing OpenRouter costs us nothing in Claude access. It simply means we stop being locked into one vendor for work that does not require them.

The part of this decision with the longest reach

The cost argument is the easiest to verify, but it is not the largest thing on offer. An API key is not a line item for one project — it is the ability to build our own software with AI as the engine. The Claude interface we admire is itself just an application someone built on top of a model; with a key, we can build the version that fits Gospel Light House specifically. An assistant that answers from our own sermon archive and cites the sermon it drew from. Semantic search across everything ever preached. Automatic show notes, subtitles and translation for the media library. Drafting help inside the tools staff already use.

None of those require a new vendor, a new contract, or a new approval — they run on the same key and the same balance as the transcript pipeline. And because different jobs suit different engines, a router is what lets each one use the right model instead of forcing every job onto a single vendor's. Section 6 sets this out in full, with the catalogue and the limits.

Read this before you read any number below

The corpus has not been measured yet. Every figure in this document assumes 1,800 transcripts averaging 55 minutes. If the real average is 90 minutes, costs rise about 45%; if it is 150 minutes, transcripts cross the pipeline's chunking threshold and costs rise more than threefold. The cost calculator takes the true average as an input. Measuring the corpus is the first task of the pilot, and it is the single assumption most capable of moving these numbers.

02

What the pipeline does today

The Transcript Theme Extraction pipeline reads a corpus of sermon transcripts and, for a given theme, tells us which transcripts engage that theme, how directly, and exactly which passages carry it. Everything below is drawn from the code, not from recollection.

What happens to one transcript

  1. Length estimate. The transcript's token count is estimated at roughly 3.5 characters per token.
  2. Under 20,000 tokens — one API call analyses the whole transcript in a single pass.
  3. Over 20,000 tokens — the transcript is split into 12,000-token chunks with 800 tokens of overlap. Each chunk is analysed in parallel, and one additional synthesis call merges the partial findings into a single judgement.
  4. The model returns strict JSON: a relevance score from 0 to 100, an explicitness rating (explicit, tangential, or absent), a reasoning paragraph, and a list of passage locations marked by exact verbatim start and end phrases.
  5. Those markers are used to cut the real passages out of the source text, which are assembled into a Word report. The quotes in the final document are the transcript's own words, located by the model but extracted by our code.

What a "run" means

A run is one theme applied to the whole corpus. At a 55-minute average, that is 1,800 API calls, roughly 24.9 million input tokens and 1.2 million output tokens. At a 150-minute average the same corpus becomes 7,200 calls and 81.2 million input tokens, because each transcript is split into three chunks plus a synthesis call — and the chunk overlap means some text is paid for twice.

Where long transcripts hurt

Crossing the 20,000-token threshold turns one API call into four. Long transcripts are disproportionately expensive on any provider — which is precisely why an expensive per-token rate compounds rather than merely adds.

The system is already provider-agnostic

This is the crux, and it deserves to be a headline rather than a footnote. The pipeline's client is a standard OpenAI-SDK client pointed at a configurable address. Its configuration file already defaults to:

There is no Claude-specific code to remove. There is no migration to fund. Switching between DeepSeek, Gemini, Claude, or anything else is a change of one configuration value, and the same code path serves all of them. This defuses the largest objection a budget-holder normally has to any technology change — what will the switch itself cost us? The answer here is: nothing. It is already done.

We can prove parity rather than assert it

The repository contains an evaluation harness that runs the same transcript and the same theme across several models simultaneously and prints a side-by-side table of relevance score, token usage, and elapsed time. It also records how many passage locations each model found and whether the transcript was chunked.

Underneath that, the pipeline enforces a strict output schema with a retry loop. A model that cannot hold the required JSON format fails loudly and visibly rather than degrading quietly. The code already keeps a list of model endpoints that reject formal structured-output requests and falls back to prompted JSON with strict parse-and-retry — direct evidence, from our own system, that format compliance genuinely varies between models and that we already detect it.

This turns "trust me, DeepSeek is good enough" into "here is the comparison table, run on our own transcripts." It is the most credible thing in this document, and it is the reason the recommendation ends in a pilot rather than a commitment.

Spending controls that already exist

Fiscal governance built into the pipeline
ControlWhat it does
Global concurrency cap Total simultaneous API calls are capped (default 12) regardless of how transcript-level and chunk-level parallelism interleave. A run cannot stampede into rate limits or runaway spend.
Resumable checkpointing Completed transcripts are recorded as they finish. An interrupted run resumes where it stopped instead of re-paying for work already done.
Raw-result cache Each run's raw analysis payloads are stored, so the Word and HTML reports can be regenerated later — new formatting, new layout, corrected typos — without paying for the analysis again.
Per-request timeout A 180-second ceiling per call, so one hung request cannot hold a concurrency slot indefinitely.
--limit N Runs the pipeline over the first N transcripts only. This is what makes a costed pilot possible before committing to the full corpus.

One clarification, for accuracy: the cache stores results so reports can be rebuilt for free. It does not deduplicate identical API calls within a run. The saving is real but it is the saving on re-reporting, not on re-analysis.

These are worth reading as fiscal governance rather than as features. Spend is bounded, interruptions are not billed twice, and a pilot can be costed before the full commitment is made.

The cost analysis

Methodology

A calculator in the repository (tools/cost_model.py) derives token volume from the pipeline's own configuration constants rather than from a guess: the 12,000-token chunk size, the 800-token overlap, the 20,000-token single-pass threshold, the 1,655-token analysis system prompt, the 477-token synthesis prompt, and an 8% allowance for schema and rate-limit retries that re-send the full input. It then prices that volume against a table of provider rates.

Anyone can re-run it and get the same answer:

python tools/cost_model.py --transcripts 1800 --avg-minutes 55

That reproducibility is what makes these numbers credible rather than rhetorical. Every assumption is a named constant that can be challenged individually — they are listed in the appendix.

Prompt caching: a smaller saving than it sounds

Our analysis system prompt is 1,655 tokens and identical on every call, so it is a natural candidate for prompt caching, which bills repeated prefixes at a fraction of the normal input rate. Both Anthropic and the OpenRouter models support it — Claude at 10% of the input rate on a cache hit, DeepSeek V4 Flash at $0.0168 per million against $0.0679 standard.

The honest arithmetic: the system prompt is about 12% of the input tokens on a 55-minute transcript. The transcript body — the other 88% — is unique to each call and cannot be cached. Caching the prompt therefore saves roughly 8–9% of a run's total cost, on any of these models. That is real and worth implementing, but it is a rounding adjustment, not a lever. It does not change any decision in this document. We list it as an implementation to-do, not as a saving to bank in advance.

What OpenRouter itself costs

OpenRouter states that it passes through provider pricing without markup on inference. We verified this directly: Claude Opus 5 lists on OpenRouter at $5 and $25 per million tokens — identical to Anthropic's own published rates. There is no hidden margin on tokens.

OpenRouter monetises instead through a credit purchase fee of 5.5% (minimum $0.80) on card payments, and a 5% fee on very high-volume bring-your-own-key usage that does not apply to us. In practice: a $100 approval buys about $94.50 of usable credit. We are naming this because a reader should not discover it on a receipt.

04

Why the price gap exists

The natural reaction to an 81× price difference is suspicion. If one thing costs 81 times another, surely it is 81 times better, and surely we are about to buy something inferior. That instinct is sound in most markets. It is misleading in this one, and the reason is worth understanding properly.

Capability varies at the frontier. Our task does not live at the frontier.

Models are not equally intelligent. The differences between a frontier model and a mid-tier one are real and, on the right task, dramatic: novel reasoning, long-horizon planning, holding a complex problem in mind across many steps, original synthesis. If we were asking a model to write original theology, or to design a research methodology from scratch, the frontier tier would be worth every cent.

That is not what we are asking. Our pipeline asks a model to do one bounded, well-specified thing, over and over:

  • Read a segment of text.
  • Judge how relevant it is to a named theme, and how directly.
  • Emit strictly-formatted JSON containing that judgement, a short justification, and the verbatim phrases that begin and end each relevant passage.

This is squarely inside what the entire current generation of mid-tier models does reliably. It is careful reading and structured reporting — a commodity operation, performed 1,800 times. At frontier prices, we are paying a specialist's consulting rate for careful transcription.

The capability gap narrowed while the price gap widened

On structured extraction specifically — read this, judge it, report it in this exact shape — the distance between the best model available and the tenth-best has compressed to near-irrelevance, while the price distance has grown. That divergence is the entire opportunity. It is not that the expensive model is bad value in general; it is that it is bad value for this particular job.

We are deliberately not quoting benchmark scores here. Published benchmarks measure general capability on tasks that are not ours, and citing them would be borrowing authority we have not earned. The argument does not need benchmarks. It needs the pilot, which measures the only thing that matters: how these models perform on our transcripts, against our themes, in our output format.

The schema is the real quality floor

The pipeline does not trust any model on faith. Every response must validate against a strict schema — score, explicitness rating, reasoning, and location markers with exact verbatim boundaries. A response that does not validate is retried; a model that repeatedly cannot comply fails visibly and gets disqualified. And because the passage markers must be exact verbatim text found in the source, a model that fabricates a quotation produces a marker our extraction code cannot locate. The failure surfaces rather than slipping through into a report.

This architecture is what makes a cheap default safe. The risk of a bad model choice is not silent degradation in a published document; it is a noisy failure at pilot stage that costs a few dollars to discover.

Choosing OpenRouter is not choosing against Claude

Where a task genuinely does need frontier capability, OpenRouter serves Claude Opus 5 on the same key, through the same code path, at the same published price — one configuration line away. Nothing about this proposal reduces our access to Claude, or makes returning to it harder. It makes returning to it a one-line decision instead of a procurement decision.

05

Subscription, API, and our own asset

Three different things tend to get conflated under the single word "Claude." Separating them clarifies what we are actually buying, what we already own, and — most importantly — why the thing we already pay for cannot be pointed at this problem.

Sold per token

The modelThe raw capability — reading, judging, writing. Priced per million tokens. This is what an API purchase buys, and it is the layer where the 81× applies.

Sold per seat, per month

The product wrapperThe Claude chat interface, Projects, file uploads, the desktop and mobile apps. Genuinely excellent, and priced for people rather than for volume. This is what our subscription buys — and it is a different purchase from the layer above it. A subscription does not include, and cannot be converted into, access to the model layer for our own software.

Built by us · owned by us

Our own infrastructureThe chunker, the concurrency gate, the retry-and-schema layer, the checkpointing, the passage extraction, the aggregation, the Word report generator. This is the asset that actually produces the deliverable — and it is provider-neutral by design.

The subscription we already pay for cannot buy this work

This is the point most likely to be misunderstood, and it is worth stating without hedging. A Claude subscription and Claude API access are two separate products, bought separately, billed separately, on separate accounts. Paying for one does not give you any amount of the other.

Anthropic states this plainly in its own support documentation:

"Claude paid plans give subscribers access to Claude on the web, desktop, and mobile… The Claude Console is our developer platform providing API keys and access to Claude models for building applications and integrations. A paid Claude subscription enhances your chat experience but doesn't include access to the Claude API or Console."

Anthropic Help Center, "I have a paid Claude subscription — why do I have to pay separately to use the Claude API and Console?"

The practical consequence for us: our subscription cannot issue an API key. Our pipeline cannot log in with it. There is no setting, no upgrade, and no support request that converts subscription usage into the programmatic access this system needs. The two purchases go through different doors.

The one exception, stated honestly

There is a narrow case that a well-informed colleague may raise, and we would rather raise it ourselves. Anthropic does let a Pro or Max subscriber use their plan for some developer tools — Claude Code, and projects built on the Claude Agent SDK — through a per-user monthly credit ($20 on Pro, $100 or $200 on the Max tiers). So it is not strictly true that a subscription buys nothing programmatic.

It does not, however, help us, for three independent reasons:

  • Wrong architecture. That credit applies to Anthropic's own Agent SDK. Our pipeline is a plain OpenAI-compatible HTTP client — deliberately, because that is what makes it provider-neutral. It cannot draw on that credit at all without being rewritten around a single vendor's framework, which is the opposite of what this proposal recommends.
  • Wrong billing unit. The credit is per user, and Anthropic states it "can't be pooled, transferred, or shared across the organization." A corpus run is organisational work, not one person's work.
  • Explicitly not for this. Anthropic's own guidance is that "teams running shared production automation should use Claude Platform with an API key for predictable pay-as-you-go billing." We agree with them. That is precisely what this proposal asks for — an API key with pay-as-you-go billing, purchased through OpenRouter so it is not tied to one vendor.
What this settles

"We already pay for Claude, so this is duplicate spend" is the objection this section exists to answer, and the answer is that the two payments cannot substitute for each other in either direction. The subscription cannot run the pipeline. API credits cannot give the team a chat interface. Declining this request does not save money by falling back on the subscription — it means the corpus does not get analysed at all.

Why the interface could not do this job even if it were free

Set billing aside entirely and the chat interface still cannot do this work. It is superb at what it is for: one person, one conversation, a handful of documents. It is structurally the wrong tool for 1,800 transcripts, and not because of any deficiency in Claude:

The distinction that matters

A subscription seat scales with people. An API key scales with work. Our bottleneck is work, not people. Both purchases are legitimate; they are simply answers to different questions, and only one of them can process a corpus.

06

One key, many applications

Everything so far has argued about the price of one job. This section argues something larger, and it is the part of the decision with the longest reach: what we are actually acquiring is not cheaper transcript analysis. It is the ability to build.

The interface we admire is itself an application

It is worth saying out loud what the Claude chat interface actually is. It is a very good application that Anthropic built on top of a model. The conversation window, the memory of what you said earlier, the file uploads, the projects — none of that is the model. It is software wrapped around a model, designed for a general audience of individual users.

Once we hold an API key, we can do the same thing. Not build a competitor to Claude — build the version of it that fits Gospel Light House specifically: that knows our archive, speaks to our congregation, follows our workflows, and lives inside the tools our staff already use. The engine is the same class of engine. The difference is that the application around it is ours, shaped to our situation rather than to the average of everyone's.

That is the shift this key represents, and it is a shift in position rather than in price: from being a tenant in someone else's product to being the owner of our own.

Different jobs want different engines — which is the argument for a router

Why this settles the vendor question

No single vendor is the best answer to all six rows, and committing to one means accepting their weakest row as our ceiling. On a router we never have to choose: each application picks the engine that suits it, on the same key and the same balance, and changes its mind later for the cost of one configuration line. The router is not a cheaper way to buy one model. It is the thing that lets each job have the right one.

The governance case

This matters more to finance than to engineers. One vendor relationship. One prepaid balance. One dashboard showing spend by application. The alternative — a separate subscription per tool per team — is both more expensive and considerably harder to audit, because each subscription is a fixed monthly charge disconnected from any unit of work.

For the budget-holder

Prepaid credits mean spend cannot exceed what was deliberately loaded. If we load $100, the maximum possible exposure is $100. There is no surprise invoice, no overage, and no auto-renewing commitment. Approving a balance is approving a ceiling, not opening a tap.

What this key does not do

This section has made an expansive claim, so it should end with three honest limits. Naming them is not a retreat from the argument; it is what keeps the argument worth trusting.

Limits on the "many applications" case
The limitWhat it means for us
The key removes procurement friction, not build effort. Every item in the catalogue is a real project needing design, testing, and someone to maintain it afterwards. What the key changes is that none of them requires a new vendor, a new contract, a new invoice, or a new approval — so the question becomes "is this worth building?" rather than "can we get permission to try?" That is a genuine change, but it is not the same as the applications being free.
Public sermon content is low-risk. Member data is not. The whole data-sovereignty answer in section 8 rests on these being public sermons — already published, containing nothing personal or confidential. Anything touching member records, pastoral notes, giving history, or safeguarding matters is a different risk category and needs its own decision, its own provider restrictions, and probably its own legal review. This approval should not be read as covering that, and we are saying so deliberately rather than letting the scope drift later.
Member-facing tools need a higher bar than internal ones. An assistant answering a member's question about what the church teaches can be confidently wrong, and the cost of that is pastoral, not financial. Anything member-facing needs to cite back to a specific sermon so a person can check it — the same verbatim-passage discipline the transcript pipeline already enforces — and needs human review before launch. The internal and media tools in the catalogue carry no such exposure and could move much sooner.
07

Optionality and hybrid tiering

The durable argument for this decision is not "DeepSeek is cheapest today." Prices and rankings move every few months, and any document that rests on today's leaderboard is obsolete by Christmas. The durable argument is optionality.

  • Hundreds of models behind one endpoint and one key. Including every Claude model, at Anthropic's own prices.
  • Switching is one configuration value — proven, because it is how the system is already built.
  • Automatic failover. If a provider has an outage or rate-limits us, the run can continue on another. A single-provider setup simply stops.
  • Price competition works for us continuously. When something cheaper or better ships, we adopt it the same week rather than renegotiating a contract.
  • No lock-in. If Claude becomes the right answer next year, we move back — same key, same code, same afternoon.

The hybrid tiering proposal

Here is what we actually recommend running, and it is not a cost-cutting design. It is an allocation design.

Two-tier production configuration · per theme, 55-minute average
PassModelTranscriptsPurposeCost
Bulk DeepSeek V4 Flash 1,800 Score and locate passages across the whole corpus $1.89
Adjudication Claude Sonnet 5 150 Independently re-score the highest-relevance transcripts — the ones destined for publication $5.13
Total— Frontier-grade confidence exactly where a mistake would be visible $7.02

Note what the second pass buys. It is not a spot check for reassurance. It is a genuine second opinion from a materially different model on every transcript whose findings will actually be quoted in a report — and where the two passes disagree, that disagreement is itself a signal worth reviewing. We get more scrutiny on the published material than a single-model run at any price would give us, because a single model cannot disagree with itself.

Reframe

This is not cutting corners. It is intelligent allocation: cheap capacity where the work is bulk and verifiable, expensive capacity where the stakes are visible. Spending $154 to apply frontier reasoning uniformly — including to the 1,650 transcripts that turn out to score near zero — is not rigour. It is undirected spending.

08

Risks and objections

A proposal that hides its trade-offs looks naive. Here are the objections we expect, stated as fairly as we can, with our answers.

Objections and responses
ObjectionResponse
"Cheap models will produce worse analysis." Possibly. We do not have to speculate — the evaluation harness measures it on our own transcripts, and the pilot is designed to answer exactly this. Decide on the evidence, not on this document. The hybrid adjudication pass in section 7 is the standing safeguard if the answer is "slightly worse, but only on hard cases."
"DeepSeek is a Chinese model. What about data sovereignty?" A fair question, and we will not dodge it. Two things. First, the data: these are sermon transcripts — public teaching, already published in audio form. No personal, financial, or pastoral-confidence data passes through the pipeline. Second, the control: OpenRouter publishes each provider's data-retention and training policy, lets an account opt out of routing to providers that train on submitted data, and allows individual requests to be restricted by data policy; enterprise accounts can additionally route through EU or US regional endpoints. If the concern persists after that, Gemini 3.5 Flash Lite is a Western-hosted alternative at $10.40 per run — still 15× cheaper than Opus. That this option exists on the same key, for the price of one config line, is the argument for OpenRouter.
"Another vendor to manage." It replaces per-tool subscriptions with one prepaid account and one dashboard. Fewer relationships, not more — and a spending ceiling instead of a recurring charge.
"What if OpenRouter goes down, or shuts down?" OpenRouter speaks the standard OpenAI-compatible protocol. Redirecting the pipeline to a provider's own endpoint — Anthropic's, Google's, anyone's — is a change to the endpoint address. The abstraction is the protection. This is the same property that makes the migration free in the first direction.
"We already pay for Claude. This is duplicate spend." It cannot be duplicate spend, because the two purchases are not interchangeable. A Claude subscription "doesn't include access to the Claude API or Console" — Anthropic's own words. It buys seats on the chat apps; it cannot issue an API key, and no subscription tier can run this pipeline. Declining this request would not save money by falling back on what we already pay for; it would mean the corpus is not analysed. Separately, and even setting billing aside, this is batch machine work a chat interface structurally cannot do — no programmatic loop, no checkpointing, no validated output, no per-run costing. See section 5, which also covers the one narrow developer credit that exists on Pro and Max plans and the three reasons it does not apply here.
"Exotic models will be unreliable, or rate-limit us." Some will. Schema validation with a retry loop catches malformed output; the global concurrency cap of 12 and per-request 180-second timeout bound the blast radius; checkpointing means a failed run resumes rather than restarts. Failure is visible and resumable rather than silent. What we cannot promise in advance is latency — cheaper models are not automatically faster, and a slower model on a rate-limited endpoint could make a full run take materially longer. The pilot measures elapsed time per call, which is precisely why it reports latency alongside cost.
"JSON compliance varies by model." True — and this, not raw intelligence, is the real selection criterion. Our code already carries a fallback path for model endpoints that reject formal structured-output requests, which is direct evidence that the variation is real. The pilot measures it. Any model that cannot hold the format is disqualified at pilot stage for a few dollars, before it is anywhere near a published report.
"The savings look too good. What is the catch?" Three, named plainly. One: the corpus average is unmeasured, and if transcripts average 150 minutes rather than 55, every figure here roughly triples. Two: the 81× is a ratio between two small numbers — the absolute saving on a single run is $152, which is real but not transformative on its own; the case rests on repetition across themes and iterations. Three: we have not yet demonstrated quality parity on our own data. That is what the pilot is for, and it is why this document asks for a pilot rather than a decision.
